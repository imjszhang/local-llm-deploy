# Local LLM Deploy 重构计划

日期：2026-09-13。状态：已按本计划实施，验收记录见 [validation.md](validation.md)。常驻服务保留原进程，实际上线切换按 [migration.md](migration.md) 执行。

目标：让新增模型、升级推理引擎、修改网关和排查运行问题都有明确入口，减少跨脚本修改，并能通过自动化验证后逐步切换。

本轮按“兼容现有入口、分阶段替换”实施，优先支持当前 macOS / Apple Silicon 环境。有意改变的路由、认证、依赖安装和删除规则单独记录在 [compatibility.md](compatibility.md)。以下保留原计划的阶段划分；实际模块命名和职责以 [architecture.md](architecture.md) 为准。

## 1. 现状与重构重点

| 现状 | 维护成本 | 对应改造 |
| --- | --- | --- |
| `serve-ui.py` 约 1900 行，包含配置、发现、监控、调度、HTTP、日志、知识库代理 | 小修改容易影响不相关请求路径 | 按职责拆分，显式传递依赖 |
| `type` 混用 `embedding/asr/rerank` 与 `ollama/external` | 模型能力与运行方式耦合，路由需要排除法 | 分离能力、后端实现和生命周期归属 |
| 多个 Python 文件和 Shell 内嵌 Python 重复解析配置 | 默认值、注释键、路径和覆盖顺序不一致 | 唯一的配置加载与校验模块 |
| PID 文件、`pgrep`、端口探测、launchd 状态分散 | CLI 与网关可能对同一服务给出不同判断 | 统一服务实例与状态探测 |
| `manage.sh` 转交服务脚本，脚本又写死模型名和端口默认值 | 添加同类模型仍需修改脚本 | 模型配置生成启动描述，运行方式负责执行 |
| 不同 llama.cpp 目录、特定 PR、宽松 Python 版本约束 | 升级结果难复现，失败后回退依据不足 | 引擎配置档案、分环境依赖约束、明确升级记录 |
| 测试集中于 Embedding 在线冒烟 | 路由、取消和并发问题容易在真实调用时才发现 | 无模型契约测试 + 独立真实服务验证 |

代码依据包括：`serve-ui.py` 的 `get_running_models`、`_resolve_model_from_body`、`_forward_with_keepalive`；`manage.sh` 的 `cmd_start`；`jina.sh` 的 `configure`；`deploy.sh` 的端口处理；`setup_llamacpp.sh` 的 PR 切换逻辑。

## 2. 本轮范围与架构决定

本轮建立一个可安装的轻量 Python 包，把现有 Shell 入口逐步缩减为兼容包装。网关与各模型服务保持独立进程，Embedding、Rerank、ASR 保持独立依赖环境。网关和 CLI 不导入 PyTorch、MLX 或实际模型代码。

初期保留标准库 HTTP 服务和线程模型。先把路由、调度和转发从 HTTP handler 中分离，框架迁移留给独立评估；避免同时改变目录、并发模型和协议行为。调度状态仍由单个网关进程持有，多 worker 会破坏当前全局并发约束，因此不在本轮启用。

现有 `manage.sh`、`serve-ui.sh`、`jina.sh`、`whisper.sh`、`ds4.sh`、`deploy.sh` 及 Python 服务入口均保留。`models.json`、密钥文件、权重目录、模型别名、端口、日志路径也保留。改变错误路由、认证和进程误操作等行为时，用独立变更说明和测试标识，不混入纯文件搬迁。

本轮不引入数据库、消息队列、容器编排或分布式调度，不重写监控 UI，不扩展为模型训练或知识库平台，不搬迁或重新下载已有权重。前端只做资源拆分、API 兼容和必要的认证接入。

## 3. 统一三个核心概念

### ModelSpec：模型定义

描述“模型能做什么、由什么提供”：模型键、别名、能力集合、后端类型、后端模型 ID、下载来源、默认运行参数。

- 能力：`chat`、`embedding`、`rerank`、`asr`。
- 后端类型：如 `llama_cpp`、`ollama`、`transformers_embedding`、`mlx_rerank`、`mlx_whisper`、`external_http`。
- 生命周期归属：本项目管理或仅发现/连接；Ollama 与外部服务默认仅连接。
- 支持的 API 路径单独声明；能处理 chat 不等于支持 `/v1/responses` 或 `/v1/messages`。

旧配置读取后转成内部统一结构。初期不强制重写用户的 `models.json`；旧 `type` 的映射、未知字段保留策略和冲突错误均通过配置测试固定。新字段先作为向后兼容扩展。

### ModelInstallation：权重安装

描述“哪一份权重在哪里”：模型键、量化、实际路径、来源 revision、完整性检查结果。既有 `.manifest.json` 继续作为安装登记来源；默认目录推导与显式安装记录分清职责。

启动、下载、`models` 和 `remove` 使用同一个路径解析器。显式指定路径或安装记录优先；没有指定时仅在选择唯一、无歧义时使用默认路径。登记了多个同量化安装时要求明确选择，避免任意选取目录。

### ServiceInstance：服务实例概念

描述“某服务现在怎么运行”：实例 ID、模型键、地址、后端模型 ID、运行方式、进程身份、健康状态、启动时间和引擎版本。网关本身也是服务，但不作为模型出现在 `/v1/models` 中。

把进程存活、端口可连接和服务就绪区分开。状态查询只读取；失效记录清理由生命周期操作或显式 reconcile 命令处理。

实施时统一为 `lifecycle.types.InstanceObservation`，启动描述为 `ServiceSpec`；没有另建一份重复的 `domain.ServiceInstance`。测试按职责保存在 `tests/test_*.py`，显式本机验收位于 `tests/smoke/`，不提前建立空测试目录。

迁移初期继续读取已有 PID 文件并生成统一的内存状态。不要在第一阶段引入另一份同等权威的状态文件。将来确需新文件格式时，增加版本、原子写入和旧格式读适配，并明确唯一写入者。

## 4. 建议目录与依赖边界

```text
src/local_llm_deploy/
  cli.py                    # 命令解析、输出与应用编排
  config.py                 # 注册表、环境配置、校验、兼容转换
  domain.py                 # ModelSpec / ModelInstallation / ServiceInstance
  registry.py               # 注册表读写与配置缓存
  artifacts/                # 下载、权重路径、安装清单、删除规则
  lifecycle/                # 服务启动/停止/状态、进程身份与就绪检查
    process.py              # 普通本地进程执行
    launchd.py              # macOS LaunchAgent 生成与控制
  backends/                 # 启动参数构建、能力声明、协议差异适配
  gateway/
    app.py                  # HTTP 入口和依赖组装
    discovery.py            # 本地、Ollama、外部后端发现
    routing.py              # model/alias/能力匹配、请求目标解析
    scheduling.py           # lane、模型预算、请求占用与释放
    transport.py            # HTTP 转发、SSE、取消、错误与超时
    auth.py                 # 模型 API 认证策略
    monitoring.py           # 系统、模型与队列状态接口
    knowledge.py            # 独立知识库反代
  services/
    common.py               # 小范围共享 HTTP/健康检查/错误辅助函数
    embedding.py            # Embedding 服务与模型适配
    rerank.py               # Rerank 服务与模型适配
    whisper.py              # Whisper 服务与模型适配
  observability.py           # 日志上下文、请求 ID、耗时和脱敏
static/                     # 保留页面；按需抽取 JS/CSS
tests/
  unit/
  contract/
  integration/
  smoke/                    # 显式启用的本机真实模型测试
pyproject.toml
constraints/                # 按运行环境保存已验证的依赖解析结果
docs/
  architecture.md
  refactoring-plan.md
  development.md
  upgrade.md
  migration.md
```

目录按实现进度建立，不提前创建空抽象。

依赖方向：CLI / 网关 / 模型服务调用配置与领域模块；网关使用发现、路由、调度、转发；生命周期使用后端生成的启动描述。领域模块不依赖 HTTP 或 Shell。重型模型库仅存在于对应服务的运行路径。

两类适配器职责必须分开：后端适配器生成命令参数、声明协议与能力；运行适配器处理 process / launchd 的启动与停止。不要为每个模型重复实现一套生命周期，也不要提前设计动态插件框架。

## 5. 分阶段实施

### P0：记录契约并建立可重复验证的基线

工作：

- 整理 CLI 参数、退出码、配置覆盖顺序、HTTP 路径、响应字段和日志/状态文件格式。
- 为网关创建轻量假后端，可模拟流式、慢响应、异常、断开和 multipart；所有测试使用临时目录与端口。
- 标记现有已知问题：应保留的兼容行为与后续明确修复的缺陷分别记录，缺陷不作为永久兼容要求。
- 增加测试命令与 CI 基线；普通测试无需 GPU、模型下载、launchd 或在线模型服务。
- 记录本机真实服务的基线验证方法；正式迁移时再按阶段执行小样本，不自动运行耗时 benchmark。

验收：可以重复验证别名路由、JSON、SSE、Embedding、Rerank、Whisper 协议封装及脚本参数；模拟后端测试不碰真实密钥和运行目录。

建议交付：1 个基础 PR。先通过兼容测试；后续缺陷用独立回归测试推进。

### P1：建立轻量包，统一配置与权重路径

工作：

- 加入 `pyproject.toml`、`src` 包和显式项目根目录配置；记录支持的 Python 版本。
- 定义三个领域结构，把配置加载、默认值和校验收敛到单处；库函数返回结果/异常，退出码由 CLI 处理。
- 先完整记录旧的参数优先级，再分开实现新规则。目标是 CLI > 环境变量 > 模型配置 > 默认值；`.hf-env` 等文件的具体作用域明确记录，差异单独迁移。
- 合并路径解析和安装选择；注册表与 manifest 更新使用原子写入，读改写操作有锁，避免并发下载覆盖登记。
- 规定别名冲突、端口冲突和模型能力错误的诊断方式。明确配置生效范围：注册表刷新校验成功后整体替换，活动请求保留快照；监听地址、环境变量与调度预算首轮采用重启生效，避免注册表已变而旧 gate 仍使用旧预算。
- 提供轻量安装/检查入口；切换包装脚本前，在各虚拟环境验证包可导入，避免依赖当前工作目录或临时 `PYTHONPATH`。

验收：旧 `models.json` 和样例均可读取；CLI、网关与服务解析同一模型得到一致结果；`list/status` 无需安装模型推理依赖；路径测试覆盖嵌套 GGUF、多安装、别名、注释键和特殊字符。

建议交付：2 个 PR，分别处理包/配置与权重/清单。

### P2：拆分网关，保持现有可用行为

工作：

- 抽离模型发现和纯路由逻辑，再抽离调度器与转发器，最后处理监控、日志和知识库。
- 用显式应用上下文替换模块级缓存与全局对象；测试可注入注册表、时钟、发现结果及传输实现。
- HTTP handler 只做协议输入输出和调用编排，保留旧 `serve-ui.py` 为启动包装。
- 保持默认 chat/Embedding/ASR 并发设置、SSE 保活、API 响应字段及 `/knowledge/` 路径重写和客户端凭据转发。

验收：P0 兼容测试通过；新旧网关使用假后端可作同输入差异比较；单网关进程内跨模型并发行为一致。真实服务只做一次代表性验收，结构 PR 不顺手调整参数或升级库。

监控当前的 `queue_depth` 可能包含活动请求，必须在 P0 记录其语义；需要新增纯等待数时采用新增字段，不在结构拆分中悄悄改变旧字段和队列上限的含义。

建议交付：2 个 PR，拆分发现/路由和调度/转发。

### P3：单独修复路由、认证和请求取消

| 项目 | 目标行为 | 验证重点 |
| --- | --- | --- |
| Rerank 路由 | `/v1/rerank` 根据能力及模型选择重排序后端，有独立可配置并发限制，初始为 1 | 显式模型、别名、无可用后端、上游错误 |
| 未知模型 | 显式未知模型返回 404，不回退到其他模型；模型存在但不可用返回 503 | 不能发生跨模型误路由 |
| 缺失模型 | 仅允许配置中明确的默认模型；没有默认时返回 400 | 不依赖目录或字典枚举顺序 |
| 能力与协议匹配 | Chat 不选择 Rerank；端点能力不足返回明确错误 | `/responses`、`/messages` 不能被宣称为所有后端均支持 |
| API 认证 | 所有模型代理统一认证，包含 `/v1/*`、`/api/<model>/*`、默认 `/api/*` 转发及 Ollama 推理/操作代理；只读监控例外必须按路径白名单声明 | 不可借代理自动注入的密钥绕过校验 |
| 监控认证兼容 | 为监控的状态接口明确只读策略；需鉴权的后端请求由页面支持输入 Key 并在会话内使用 | 页面继续可用，不把服务端 Key 写入静态资源 |
| 知识库凭据 | 继续转发知识库客户端凭据，与模型 API Key 分开处理 | 不覆盖知识库 Authorization |
| 流式取消 | 下游断开后停止读取并尝试关闭上游，任务完成/清理后准确释放 lane/KV | 排队断开、推理断开、上游不及时停止、无重复释放 |

特别处理 SSE 状态语义：发送响应头前的错误用正常 HTTP 状态；为排队保活而已经发送 200 后，错误必须按该端点的流式协议表达。Chat、Responses、Messages 不共用未经验证的结束事件模板。

上游连接关闭不等于模型立即停止计算。调度器应在正常完成或后端确认终止时释放推理占用；取消无法确认时，保守保留占用并等待可观测的结束或空闲状态。达到超时仍无法确认的实例标记为状态不确定，阻止该实例新增推理，通过显式 reconcile 检查或重启恢复。传输缓冲等本地资源应及时清理，不能用“客户端已断开”作为推理已结束的唯一证据。各后端的取消确认能力在适配器中明确声明与验证。

为流式缓冲设置边界，避免慢客户端或可选响应日志导致无上限内存增长。请求状态用明确的排队、运行、取消、完成与失败转换表达；无论哪个异常分支，资源只释放一次。

验收：上述场景均有回归测试；并发错误路径结束后队列、槽位与预算恢复正确值；真实客户端验证 SSE、监控认证和知识库调用。改变默认行为前更新迁移说明并检查本机调用方。

建议交付：2 个 PR，分别处理路由/认证与取消/资源管理。

### P4：统一 CLI 和服务生命周期

工作：

- Python CLI 逐个接管 `registry/list/models`、`download/register/remove`、`start/stop/status/logs`；Shell 只负责选择解释器、转发参数与信号。
- 后端适配器构造 `ServiceSpec`（argv、工作目录、环境变量、解释器、日志、就绪检查）；运行适配器统一处理 process / launchd。
- 启动过程增加同实例互斥、端口检查、就绪等待与失败清理；区分 starting 与 ready，只在端口成功绑定、服务就绪后对路由发布 ready 状态。端口被无关进程占用时返回错误，不直接终止占用者。
- PID 只作为进程身份的一部分，结合启动时间、命令路径或 launchd label 检查归属；停止操作不依赖宽泛 `pgrep`。
- 模型标识、端口和已解析配置完整传递到 launchd，不在 Jina/Whisper 包装脚本中再次写死；支持多个同类模型实例。
- Ollama/外部服务可查询和连接，但不会因 `stop --all` 被当成本项目进程终止。
- 保留现有 LaunchAgent label、入口路径及各服务的 `RunAtLoad` / `KeepAlive` 策略；已安装服务在受控重启时切换实现，读取状态不自动重装 plist。
- 权重删除在同一生命周期视图中检查使用者，拒绝删除模型根目录、越界符号链接目标和仍被实例使用的共享权重。

验收：假进程和临时文件验证重复 start/stop、崩溃记录、PID 复用、端口冲突、启动失败和共享权重；专用 macOS 环境验证 launchd 登录自启、异常恢复及 stop 行为；老命令的参数与退出码保持兼容，主动改变的幂等语义另行记录。

建议交付：2 个 PR，分别处理 CLI/启动描述与生命周期/launchd。P1 完成后可与 P2/P3 并行开发，真实环境切换仍逐项进行。

### P5：整理推理服务、引擎和依赖升级方式

工作：

- 将三个服务搬入包，仅提取实际重复的 HTTP、健康检查、错误和配置辅助代码。保留 Embedding adapter 锁、ASR 推理锁、设备选择及现有输出格式。
- 分离 core、下载、Embedding、Rerank、Whisper、开发依赖；分别生成并验证约束文件，补齐当前未单独声明的 Embedding 环境。
- 普通启动/下载命令遇到缺失依赖时给出安装方法；依赖安装和升级由明确的维护命令承担，避免任务运行时隐式升级环境。
- llama.cpp 采用具名引擎配置档案，记录仓库、精确 commit、构建参数、可执行文件和验证结果。支持模型指定引擎档案，并继续接受 `CPP_DIR` 覆盖。
- 编译脚本不再默认拉取并切换特定历史 PR；实验 PR 和新引擎在独立目录构建，验证后更新引用，旧构建保留用于回退。
- 固定下载 revision 的配置能力与清单记录贯通；Jina 模型目录内加载的 Python 代码也纳入 revision 记录。
- 外部 Ollama/DS4 记录可观测版本和协议能力，本轮不接管其安装升级。

验收：轻量环境独立执行 CLI 和网关；三个模型环境可按文档重建并完成小样本推理；同一后端的新模型通常只需配置；新后端的专属变更集中在适配器和契约测试；能切回上一已验证引擎而不更改权重。

建议交付：2 个 PR，分别处理服务/依赖与引擎更新流程。运行包的基本安装在 P1 完成，P5 是复现与升级流程完善。

### P6：收尾、文档与维护验收

- 更新架构、部署和 API 文档，移除不存在的 `chat.html` 指引和过期模型清单；当前可用模型由注册表展示。
- 增加开发、迁移和升级手册，写清“添加同类模型”“接入新后端”“更新引擎”“排查请求排队”的入口。
- 监控页面按实际需要抽取 JS/CSS，保持页面功能和 URL；不为目录整齐而引入前端构建系统。
- 移除已失去调用者的重复实现和临时迁移分支，保留对外兼容包装；约束文件、格式检查和无模型测试进入 CI。
- 演练一次真实升级与回退；记录完整验证结果和已知限制。

验收：从干净 checkout 可完成轻量环境安装与测试；开发者能仅依文档接入一个同类模型；根目录入口不再包含领域逻辑；本轮涉及的契约均有可重复验证方法。

建议交付：1 个收尾 PR。合计约 12 个独立评审单元，实施时可按差异大小调整；P0 后再依据测试成本估算工期。

## 6. 测试与迁移规则

| 层级 | 覆盖内容 | 运行条件 |
| --- | --- | --- |
| 单元 | 配置、路径、别名匹配、能力、启动参数、调度状态转换 | 每次相关变更，无模型 |
| 契约/集成 | JSON/SSE/multipart、上游错误、取消、认证、旧 CLI 和 PID 格式 | CI 假后端、临时目录和子进程 |
| 平台 | plist 参数、登录自启、异常退出、归属判断 | 专用 macOS 验证，不影响常用服务 |
| 真实冒烟 | Chat 普通/流式、Embedding task/维度、Rerank 排序字段、Whisper text/json/verbose_json | 阶段切换时，在现有硬件上显式运行 |

测试检查对外行为及关键资源约束，不为文件移动编写镜像实现测试。真实模型输出不要求字节一致；结构、数值维度、状态码、能力和请求完成情况必须符合约定。

每个阶段独立提交，先通过自动化验证再安排服务重启；以备用端口测试新网关时使用假后端，连接真实模型做验证必须串行，避免两份网关各自调度造成总并发失控。不镜像真实推理流量。

切换前记录代码版本、依赖环境、有效配置及引擎引用；如涉及 plist 更新也保留上一份定义。配置和权重保持原位，已有进程可继续使用旧入口直到对应阶段完成。

结构调整可通过恢复旧代码入口回退；有意改变路由/认证时只对相应行为 PR 单独回退。依赖升级在可替换环境中验证并保留旧环境；引擎回退切换已验证引用，不重新编译未知版本。涉及运行状态的回退必须先协调停止新实例并确认端口释放，不能只覆盖 PID 文件。

## 7. 完成标准

1. 新增同后端模型只需配置与权重登记，通用 Shell 和网关无需增加模型名分支。
2. 配置解释、权重定位、实例状态各有单一实现，CLI 与网关结果一致。
3. 网关路由、调度、传输和监控可独立测试；更换 HTTP 实现不需要重写领域逻辑。
4. 无关进程不会被启动/停止命令误操作，实例状态与就绪状态可区分。
5. 已知的 Rerank 路由、未知模型回退、认证绕过与请求取消问题有明确行为及测试。
6. 现有模型权重与外部调用入口继续可用，主动改变的行为有迁移说明。
7. 引擎与依赖升级有确定版本、验收记录和经过演练的回退路径。
